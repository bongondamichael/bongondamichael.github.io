LOG #5 — Developer Insights (le site) Kinshasa, RDC Mon premier déploiement, ou l'art de se débrouiller sans tout comprendre

Un raccourci qui fonctionne aujourd'hui se paie plus tard

Petite confession : mon tout premier push sur GitHub, je l'ai fait sur une branche appelée master. Pas main, celle que tout le monde utilise aujourd'hui. Pourquoi ? Parce que c'est le nom par défaut dans VS Code, et que je n'avais aucune idée qu'il fallait s'en soucier.


Résultat : je bloquais sur comment gérer cette histoire de branches. Alors j'ai fait ce que beaucoup de devs débutants font sans le dire — j'ai contourné le problème. Direct sur l'interface web de GitHub, bouton "Upload files", je glisse mon index.html, je commit, et voilà. Le site est en ligne.


Ça a marché. Le site tourne, l'URL est propre (bongondamichael.github.io), tout fonctionne. Mais ce raccourci a un coût que je découvre maintenant : pas de git clone en local, donc pas de flux normal pour modifier le site plus tard. Chaque petit changement voudrait dire re-télécharger le fichier, l'éditer, et re-uploader à la main. Ça marche, mais ça ne scale pas.


La leçon, et c'est celle-là qui compte : un raccourci qui fonctionne aujourd'hui n'est pas gratuit. Il se paie plus tard, en friction. Ce n'est pas grave d'avoir bricolé pour lancer vite — c'est même souvent la bonne décision au bon moment. Mais il faut savoir revenir dessus une fois que le bricolage commence à coûter plus cher que la solution propre.


Ce que je fais maintenant : je clone le repo en local pour retrouver un vrai flux git add / commit / push. Plus besoin de repasser par l'upload web à chaque modification.


Prochain log : on attaque enfin le CSS — comment un logo devient une palette, une police, et quelques lignes de code qui font tenir tout le site debout.


— Michaël, Developer Insights


LOG #4 — Developer Insights (le site) Kinshasa, RDC Le CSS, ou comment faire parler un logo

Le CSS n'est pas "rendre joli après coup"

J'avais mon logo. J'avais mon HTML tout nu, sans une seule couleur. Et je me suis posé la question que je me pose jamais assez tôt : c'est quoi le logo qui essaie de me dire, en fait ?


Deux chevrons de code — < et > — avec une flèche qui monte à travers des barres de croissance. Traduction simple : le code comme moteur de progression. Pas juste "je sais coder", mais "je construis un truc qui grandit". Ça collait exactement à l'esprit du manifeste que j'avais déjà écrit avant même de voir le logo final. Coïncidence ? Non, juste la preuve que le fond et la forme se rejoignent quand c'est cohérent depuis le début.


À partir de là, j'ai extrait une palette de 5 couleurs seulement : un fond quasi noir avec une pointe de bleu nuit, et un seul bleu accent — celui du logo. Pas de dégradé arc-en-ciel, pas de deuxième couleur d'appoint. Une seule couleur à défendre, ça oblige à être discipliné. Le twist technique du jour, celui qui m'a fait sourire : au lieu de mettre le logo en image, je l'ai transformé en masque CSS. Concrètement — le logo devient une forme "poinçon", et le navigateur verse la couleur que je veux à travers ce poinçon. Résultat : le jour où je change mon bleu, le logo change avec, automatiquement, sans toucher un seul fichier image. Le style ne décore plus le contenu — il en fait partie.


Deux autres trucs découverts en creusant : — la numérotation de mon manifeste (01, 02, 03...) n'existe nulle part dans mon HTML. C'est le CSS qui compte tout seul. — les petites fenêtres "terminal" pour mes chapitres, avec les 3 points en haut à gauche ? Zéro élément ajouté dans le code. Une seule ligne de style qui empile trois points en triangle.


La leçon du jour : le CSS c'est pas "rendre joli après coup". C'est traduire une intention en règles. Mon logo disait "progression mesurable" — mon CSS devait le prouver, pas juste l'illustrer. Capture d'écran de la palette + du site 👇 Le prochain log : je branche tout ça sur GitHub Pages. On verra si ça tient debout en vrai. Le CSS n'a jamais été si amusant à faire qu'avec Claude.


— Michaël, Developer Insights



LOG #3 — J'ai recodé le HTML à la main (et c'était pas fun 😅) Kinshasa, RDC Retour à la pratique — Coder sans IA

Ce que j'ai retenu : le HTML qui "marche" n'est pas le HTML qui a du sens

Après l'exercice du log #2 — deviner la structure d'un site sans écrire une ligne — je me suis senti prêt à passer à l'action : reprendre tout le HTML du site officiel, moi-même, sans aide.


Première tentative : catastrophe polie. Des divs partout, un h1 collé sur mon logo (alors qu'un h1 c'est censé être LE titre principal de toute la page), et des titres de section planqués dans des span au lieu de vrais h2. Bref, du code qui marche visuellement mais qui ne veut rien dire structurellement.


Le pire bug, sournois celui-là : j'avais écrit id="#manifeste" avec le dièse dans l'id lui-même. Sauf que le # c'est censé être utilisé seulement dans le lien qui pointe vers l'élément, pas dans l'id. Résultat, mon menu de navigation ne menait nulle part. Un caractère, et tout casse.


Deuxième tentative, plus propre : header et nav séparés, un vrai h1 sur la phrase du manifeste, des id sans dièse, et mes 5 clauses du manifeste transformées en vraie liste ol/li parce que — spoiler — le choix de la balise ne limite jamais le design en CSS, ça change juste le sens que ça donne à la page.


Ce que je retiens : le HTML "qui marche" et le HTML "qui a du sens" c'est pas la même chose. Le premier trompe personne à part moi.


— Michaël


LOG #2 — J'ai appris le HTML sans écrire une seule ligne Kinshasa, RDC Expérience — Apprendre sans taper

Peut-on apprendre le HTML sans écrire une ligne ?

Petite expérience bizarre cette semaine : est-ce qu'on peut apprendre les bases du HTML sans coder du tout ? Réponse courte : en partie, oui.


Le principe était simple. On me montrait un bout de HTML tout fait, et je devais deviner à voix haute ce que chaque balise faisait et pourquoi elle était là, avant de vérifier.


Exemple : un article de recette de cuisine. Pourquoi article et pas div ? Parce que ce bloc a du sens tout seul, détaché du reste — on pourrait le partager isolément et ça resterait compréhensible. Pourquoi h2 et pas h1 ? Parce que h1 est réservé au titre principal de toute la page, un seul par page.


Deuxième round : un header avec une nav, une image avec un attribut alt. Là j'ai appris un truc que je savais à moitié — alt sert à décrire l'image pour les lecteurs d'écran ET comme texte de secours si l'image ne charge pas.


Troisième round : un formulaire avec un label lié à un input. Et là, découverte : quand label et input sont bien reliés, cliquer sur le texte du label active directement le champ. Sur mobile, où viser un petit champ à la main est une galère, ce détail change tout.


Ce que ça m'a appris sur moi-même : je reconnais une bonne structure quand je la vois, bien avant de savoir la produire seul. C'est déjà une étape — la suivante, c'est transformer ce réflexe en automatisme quand c'est moi qui pars d'une page blanche.


— Michaël


LOG #1 — Le jour où j'ai chopé Claude en flagrant délit 😅 Kinshasa, RDC Anecdote et le vrai sujet

Le vrai sujet : pourquoi les bases comptent encore en 2026

Petite anecdote avant le vrai sujet. Je suis en train de refaire le HTML du site officiel à la main — no AI, juste moi et mes balises. Je renvoie mon fichier à Claude pour review, il me corrige (à raison), et il me sort une règle du genre : un span ne remplace jamais un titre de section. Sauf que... son propre fichier avait "// Manifeste" dans un span. 👀 Je lui fais remarquer. Et honnêtement, au lieu de sortir une excuse, il a juste dit "bon point, j'aurais dû faire autrement." Pas de "mais en fait techniquement...". Juste une reconnaissance directe.


Ça m'a marqué parce que ça résume où on en est en 2026 : l'IA peut te générer un site entier en 30 secondes, mais si tu connais pas les bases, tu peux même pas repérer quand elle se plante. Moi je l'ai chopé parce que je venais littéralement d'apprendre la règle deux messages plus tôt.


Soyons honnêtes, en 2026, coder tout le HTML et le CSS à la main sur un petit projet perso, c'est de moins en moins réaliste. L'IA le fait plus vite, souvent correctement. Je le vis au quotidien. Mais les bases restent non-négociables. Pas pour le plaisir de souffrir un peu en apprenant, mais parce que :


  • Tu peux pas juger un code que tu comprends pas
  • L'IA optimise pour "ça marche", pas pour "c'est propre", sans base tu le vois jamais
  • Le jour où tu dois déboguer ou comprendre ce qui se passe sous le capot, la vitesse de l'IA te sauve plus

Le vrai skill en 2026, c'est pas "je sais taper chaque ligne à la main". C'est "je sais juger chaque ligne qu'on me donne." La suite : on continue à documenter chaque étape, un log à la fois.


— Michaël


LOG #0 Kinshasa, RDC Chapitre 0 — Genèse

Pourquoi ce journal existe

J'ai grandi avec l'idée qu'il fallait choisir : médecin ou artiste. Aucun des deux n'a collé — pas parce que c'était mauvais, mais parce que ce n'était pas le truc.


Le code, lui, a collé. Pas comme une compétence à cocher sur un CV, mais comme un langage pour construire des choses qui n'existaient pas encore.


Aujourd'hui, je suis étudiant en génie logiciel à Kinshasa, et je construis en continu : Developer Insights (le site), Developer Insights (le blog), et d'autres projets qui ne verront peut-être jamais le jour — tous logués ici, sans filtre.


Developer Insights n'est pas une vitrine. C'est un journal de bord. Je préfère montrer le processus — les bugs, les migrations ratées, les décisions qu'on regrette trois semaines plus tard — plutôt qu'un portfolio poli qui cache tout le reste.


Pourquoi ? Parce que je n'ai jamais vu quelqu'un qui construit depuis Kinshasa raconter ça en direct. Les success stories africaines qu'on nous montre arrivent toujours finies, jamais en cours. Je veux logger le en cours.


Ce log #0, c'est le point de départ. Tout ce qui suit — chapitres, logs, victoires, abandons — part d'ici.


— Michaël
